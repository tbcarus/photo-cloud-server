# База данных

PostgreSQL хранит прикладные данные. Liquibase enabled=true применяет changelog `classpath:db/changelog/db.changelog-master.yml` через `includeAll: db/changelog/table`. Поставлены 14 SQL-файлов с 16 changesets. Hibernate `ddl-auto=validate`, `open-in-view=false`. Ниже результирующая схема после 01–14; это не снимок deployed DATABASECHANGELOG.

N = NOT NULL, Y = nullable, «—» = нет явного SQL default. TIMESTAMP хранится без timezone. Каждая entity-таблица имеет BIGINT identity PK `id`; user_roles — коллекция без отдельного PK.

## users

Источник: 01-user.sql, 09-refactor-user-profile.sql.

| id | BIGINT | N | GENERATED BY DEFAULT AS IDENTITY, PK |
| email | VARCHAR(128) | N | —; UNIQUE INDEX users_email_uindex(email) |
| password | VARCHAR(128) | N | — |

| banned | BOOLEAN | N | FALSE |
| created_at | TIMESTAMP | Y | — |
| last_update | TIMESTAMP | Y | — |
| display_name | VARCHAR(128) | Y | — |
| last_login_at | TIMESTAMP | Y | — |

Нет FK. Уникальность email case-sensitive в БД; normal register сохраняет lowercase. findByEmailIgnoreCase фактически сравнивает u.email = LOWER(:email), а не lower(u.email), поэтому SQL-внесённые mixed-case email нарушают ожидаемый login.

## folder

Источники: 10, 12.

| Колонка | SQL type | Null | Default / key |
| --- | --- | --- | --- |
| id | BIGINT | N | GENERATED ALWAYS AS IDENTITY; PK folder_pkey |
| user_id | BIGINT | N | FK users(id), ON DELETE CASCADE |
| parent_id | BIGINT | Y | FK folder(id), ON DELETE CASCADE |
| name | VARCHAR(255) | N | — |
| folder_type | VARCHAR(20) | N | — |
| created_at | TIMESTAMP | N | now() |
| updated_at | TIMESTAMP | N | now(); auto-update SQL trigger отсутствует |

Индексы/constraints:

- UNIQUE uk_folder_user_parent_lower_name(user_id,parent_id,lower(name)), migration 10.
- UNIQUE uk_folder_user_root(user_id) WHERE parent_id IS NULL AND folder_type='ROOT', migration 12.
- UNIQUE uk_folder_user_parent_name(user_id,parent_id,lower(name)) WHERE parent_id IS NOT NULL, migration 12.
- CHECK ck_folder_not_self_parent: parent_id IS NULL OR parent_id <> id.
- INDEX idx_folder_user_parent(user_id,parent_id).
- INDEX idx_folder_user_type(user_id,folder_type).

Два name indexes перекрываются для non-root строк. Они не запрещают произвольные другие parent=null строки. CHECK не гарантирует ацикличность, совпадение user с parent или размещение CAMERA/FILES непосредственно под ROOT. Эти правила — сервисные.

## Существенная история и ограничения схемы

Миграция 09 заменяет first/last name полями профиля. Миграция 10 удаляет `media_file` через DROP CASCADE и создаёт текущую файловую модель без переноса старых media rows. Миграция 11 переносит physical fields в StoredObject и выполняет backfill. Миграция 12 добавляет ROOT/name/self-parent ограничения. Миграция 13 снимает unique `(user, checksum)` у StoredObject. Миграция 14 добавляет FileItem.checksum, заполняет его из StoredObject и создаёт unique `(user, folder, checksum)`.

Исторические migrations 04–07 не описывают текущую таблицу или реализованные thumbnails. Миграции не перемещают физические файлы. Backfill/unique constraints предполагают совместимые существующие данные; наличие таких данных в production не установлено. Read-only SQL в `db/audit/check-file-item-folder-checksum-duplicates-before-migration-14.sql` не включён в master. Rollback/preconditions в поставляемых миграциях не предусмотрены.

Совпадение owners и двух checksum не обеспечено SQL. Parent FK не гарантирует отсутствие длинных циклов или положение CAMERA/FILES. FileItem → Folder/StoredObject имеет NO ACTION, а Folder.parent → Folder — CASCADE. Поэтому прямое SQL-удаление дерева не эквивалентно API удаления пустой папки. При удалении User SQL каскадирует его роли, коды и файловые записи; cross-owner ссылки могут остановить удаление через NO ACTION. Файлы на диске и refresh_token SQL-каскадом не удаляются.

## Транзакционно значимые операции

| Операция | Граница БД | Файловая система / предел |
| --- | --- | --- |
| Upload | TransactionTemplate: StoredObject + FileItem + cascade metadata | Final move до transaction; DTO после commit внутри cleanup catch |
| Copy | TransactionTemplate: новая пара + metadata | Files.copy до transaction; DTO после commit внутри cleanup catch |
| Owner delete | Все references → flush → StoredObject в одной transaction | deleteIfExists после commit |
| Non-owner delete | Repository delete собственной FileItem | Bytes и StoredObject сохраняются |
| Rename/move файла | Repository save; нет общей read-check-write transaction | IO отсутствует; name check неатомарен |
| Folder writes | Публичный метод Spring @Transactional | IO отсутствует; catch saveAndFlush не создаёт новую transaction |
| Email confirm/reset | Transactional dirty checking user/code | SMTP в эту операцию не входит |
| Register/login | Отдельные repository saves | Нет атомарности user/code/SMTP или lastLogin/token issue |
| JWT refresh/logout | Нет общей transaction всех чтений и записи | Refresh/revoke не сериализованы |

Repository lookup по имени с последующим save не заменяет unique constraint. План выполнения запросов и измеренная стоимость индексов не установлены: наличие `lower(checksum)` не доказывает полную неприменимость составного индекса к префиксу user/folder; `IgnoreCase` не доказывает совпадение с конкретным functional index. На token нет индекса, но фактический seq scan не измерялся.

Entity-аннотации не повторяют все SQL lengths/nullability/precision. Например, User email ограничен SQL 128, metadata exposure_time — 64, f_number/focal_length — NUMERIC(10,4), координаты — NUMERIC(10,7). Для storage integrity приоритет имеют результирующие SQL constraints.
