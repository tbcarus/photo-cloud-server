## Транзакции и удаления

[CONFIRMED] FileItemService upload/copy: filesystem до TransactionTemplate; внутри StoredObject + FileItem + metadata; return mapper после execute. Owner delete: TransactionTemplate удаляет все references + flush + StoredObject, после commit deleteIfExists bytes. Non-owner delete: только repository.delete(FileItem). Rename/move: отдельный repository.save без транзакции вокруг read-check-write.

[CONFIRMED] FolderService write methods @Transactional; getChildren/getFolderForUser readOnly. EmailRequestService confirm/reset @Transactional, dirty checking изменяет user/code. UserService register/login и JwtService flows общей @Transactional не имеют: сохранения могут завершаться независимо.

[CONFIRMED] User deletion endpoint отсутствует. При прямом SQL delete users каскады удалят его roles/email/folders/objects/items; references FileItem других пользователей на объект и NO ACTION FK могут заблокировать удаление. Удаление строки само по себе не вызывает filesystem cleanup; refresh_token не имеет FK и останется.

[CONFIRMED] Delete folder API допускает только пустую USER-папку; SQL parent cascade сам по себе рекурсивен, но не удаляет linked file_item через folder FK и может остановиться на NO ACTION. Поэтому поведение прямого SQL delete не равно API.

[RISK] Migration 10 необратимо удаляет старые metadata. Migration 11 backfill требует FileItem для каждого StoredObject и отсутствия конфликтов unique. Migration 12 требует уже валидных ROOT/names. Migration 14 упадёт на существующих дублях; подготовлен только read-only диагностический SQL [проверка дублей](C:/projects/photo-cloud-server/db/audit/check-file-item-folder-checksum-duplicates-before-migration-14.sql). Он не включён в master и автоматически не запускается. Аудит миграций не применял.
