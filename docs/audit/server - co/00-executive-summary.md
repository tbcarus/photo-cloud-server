# PhotoCloud Server — технический аудит As-Is

Дата: 10 сентября 2026. Основа: рабочее дерево репозитория при HEAD `84f7a547aabceac0849baef520605dac7111e797`.

## Область и достоверность

Аудит основан на статическом чтении production-кода, SQL/Liquibase, конфигурации, тестов и документации. Сервер и тесты не запускались, соединение с БД и SMTP не устанавливалось, физическое пользовательское хранилище не сканировалось. Версия реально развёрнутой БД, окружение процесса и прохождение тестов не подтверждены. Существовавшие до аудита удаления прежних отчётов оставлены без изменений. Созданы только новые файлы в этой директории.

Обозначения во всём пакете:

## Назначение и устройство

[CONFIRMED] Сервер предоставляет REST API личного файлового облака: регистрация и подтверждение email, login/refresh/logout, чтение профиля, upload/download, получение карточек и списков файлов, rename/move/copy/delete, дерево папок и пакетная проверка SHA-256. Клиент выбирает файл и папку; сервер определяет checksum, фактический размер, MIME, категорию и доступные metadata. Основной API — `/api/v1`; 7 controllers объявляют 36 сочетаний method/path, включая 7 заглушек с 501. Источники: пакет controller, FileItemService, FolderService, ChecksumSyncService.

[CONFIRMED] (source: build.gradle) Стек: Java 17, Spring Boot 3.4.4, Spring MVC, Security, Data JPA/Hibernate, Validation, PostgreSQL, Liquibase, JJWT 0.12.6, MapStruct 1.6.3, Lombok, Tika Core 3.1.0, metadata-extractor 2.19.0, Thymeleaf, JavaMail; Gradle wrapper 8.13. Версия приложения — 0.0.1-SNAPSHOT. Тесты используют JUnit/Mockito/MockMvc/Testcontainers PostgreSQL.

[CONFIRMED] Это один Spring Boot модуль с разделением controller → service → repository. Метаданные и логическая иерархия находятся в PostgreSQL; байты — в локальной файловой системе. `FileItem` является логическим файлом, `StoredObject` описывает его физический объект, `Folder` задаёт дерево. Переименование и перемещение меняют только БД. Копирование создаёт новые байты и новый StoredObject.

[CONFIRMED] Путь объекта: `storage.root/users/{userId}/objects/{sha256[0:2]}/{sha256[2:4]}/{physicalFilename}`. Имя включает обработанное исходное имя, UUID и расширение. Каталоги пользователей разделены; каталоги фото и видео физически не разделены. ROOT/Camera/Files — логические папки, создаваемые лениво.

[CONFIRMED] Дубликат определяется по `user_id + folder_id + checksum`. Повторный upload в ту же папку возвращает существующий FileItem с 200, сохраняя прежнее имя и timestamps. Те же байты в другой папке создают независимый физический объект. Проверка существования опирается на БД и не проверяет доступность байтов на диске.

[CONFIRMED] Аутентификация: access JWT на 20 минут, refresh JWT на 7 дней; refresh хранится целиком в БД и не ротируется при обновлении access. HTTP-сессии stateless, но серверное состояние refresh присутствует. Повторный login создаёт ещё один refresh. Logout отзывает refresh, уже выданный access остаётся действителен до expiration.

## Уровень готовности

[INFERRED] Реализация соответствует функциональному прототипу/развиваемому MVP личного облака: значительная часть файловых операций завершена по коду и имеет тестовые сценарии. Подтвердить промышленную готовность, доступность или нагрузочную устойчивость статическим аудитом нельзя; формальных критериев готовности в репозитории нет.

[PARTIAL] Полноценной синхронизации устройств нет: есть только checksum pre-check и отдельные файловые операции. Нет модели устройства, sync session, upload session, курсора изменений или tombstone-протокола. Видео сохраняется, но извлечение его длительности/metadata не реализовано. `deletedAt` предусмотрен, однако API выполняет hard delete. Sharing не предоставляется API, хотя модель допускает несколько ссылок на StoredObject.

[PARTIAL] 501 возвращают resend регистрации, resend восстановления, GET/POST страницы восстановления пароля, изменение профиля и GET/PATCH настроек. Письмо восстановления ведёт именно на страницу-заглушку. Ограничитель повторных email-запросов существует как неиспользуемый метод. Задач уборки temp/orphan/старых токенов нет.

## Наиболее существенные риски

| Метка | Наблюдение и последствие |
| --- | --- |
| [RISK] HIGH | HttpLoggingFilter пишет JSON bodies и query strings без маскировки: пароли, токены, email-коды могут попасть в INFO-логи; EmailService также пишет HTML письма |
| [RISK] HIGH | JwtAuthenticationFilter и refresh flow не проверяют enabled/banned повторно; блокировка не останавливает доступ с уже выпущенными токенами |
| [RISK] HIGH | ContentCachingResponseWrapper оборачивает в том числе download: подавление вывода binary не устраняет кэширование полного ответа в памяти |
| [RISK] HIGH | Файловая система и БД не имеют общей транзакции: аварийное завершение процесса может оставить orphan; фонового восстановления нет |
| [RISK] HIGH | Миграция 10 удаляет media_file без переноса записей; миграции 11/14 требуют совместимых существующих данных |
| [INCONSISTENCY] | Move файла не проверяет checksum target-папки: конфликт БД может стать 500 DATABASE_CONSTRAINT_VIOLATION, тогда как copy выдаёт 409 |
| [RISK] MEDIUM | Защита имён файлов — предварительный запрос без уникального DB constraint; параллельные операции могут нарушить правило имён |
| [RISK] MEDIUM | Репозиторий содержит JWT-подобные литералы в HTTP-примерах; их значения в аудит не перенесены и действительность не проверялась |

Начинать чтение следует с 01–02; для клиентского аудита достаточно восьми файлов `client-handoff/`. Полная трассировка компонентов и контроль полноты находятся в 18.
