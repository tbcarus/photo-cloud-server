# 04. Database

> Физическая схема PostgreSQL, восстановленная по Liquibase-changelog'ам `src/main/resources/db/changelog/table/*.sql` и сверенная с JPA-сущностями.

## 1. Механизм миграций

**[CONFIRMED]**

| Параметр | Значение | Источник |
| --- | --- | --- |
| Инструмент | Liquibase (`org.liquibase:liquibase-core`, версия управляется Spring Boot BOM) | `build.gradle` |
| Master changelog | `classpath:db/changelog/db.changelog-master.yml` | `application.yml` |
| Включение | `spring.liquibase.enabled: true` — миграции применяются при каждом старте | `application.yml` |
| Формат | `--liquibase formatted sql` | все файлы `table/*.sql` |
| Стратегия подключения | `includeAll: path: db/changelog/table` — **порядок определяется лексикографически по имени файла** | `db.changelog-master.yml` |
| Закомментировано | второй `includeAll` для `db/changelog/data` (каталога нет) | `db.changelog-master.yml` |
| Hibernate | `ddl-auto: validate` — схему не меняет, только проверяет соответствие сущностям | `application.yml` |
| В тестах | тот же changelog, БД — Testcontainers `postgres:16-alpine` | `application-test.yml`, `AbstractIntegrationTest` |

**[CONFIRMED][RISK]** `includeAll` с числовым префиксом `01..14` работает, пока номера двузначные. При появлении файла `100-*.sql` лексикографический порядок сломается (`100` < `11`).

**[CONFIRMED]** Rollback-блоков (`--rollback`) нет ни в одном changeset — откат миграций невозможен штатными средствами Liquibase.

### 3.5. `folder`

| Колонка | SQL-тип | NULL | Default | Комментарий |
| --- | --- | --- | --- | --- |
| `id` | `BIGINT GENERATED ALWAYS AS IDENTITY` | NOT NULL | identity | PK `folder_pkey` |
| `user_id` | `BIGINT` | NOT NULL | — | FK |
| `parent_id` | `BIGINT` | NULL | — | self-FK; `NULL` только у ROOT |
| `name` | `VARCHAR(255)` | NOT NULL | — | |
| `folder_type` | `VARCHAR(20)` | NOT NULL | — | |
| `created_at` | `TIMESTAMP` | NOT NULL | `NOW()` | |
| `updated_at` | `TIMESTAMP` | NOT NULL | `NOW()` | |

- **PK:** `folder_pkey (id)`
- **FK:**
  - `user_id → users(id) ON DELETE CASCADE`
  - `parent_id → folder(id) ON DELETE CASCADE` (рекурсивный каскад по дереву)
- **CHECK:** `ck_folder_not_self_parent`: `parent_id IS NULL OR parent_id <> id`
- **Unique-индексы:**
  - `uk_folder_user_parent_lower_name` — `UNIQUE (user_id, parent_id, lower(name))` (migration 10)
  - `uk_folder_user_root` — `UNIQUE (user_id) WHERE parent_id IS NULL AND folder_type='ROOT'` (migration 12)
  - `uk_folder_user_parent_name` — `UNIQUE (user_id, parent_id, lower(name)) WHERE parent_id IS NOT NULL` (migration 12)
- **Индексы:** `idx_folder_user_parent (user_id, parent_id)`, `idx_folder_user_type (user_id, folder_type)`

**[CONFIRMED][INCONSISTENCY]** `uk_folder_user_parent_lower_name` и `uk_folder_user_parent_name` полностью перекрываются для строк с `parent_id IS NOT NULL`. Второй избыточен (первый уже это гарантирует), но безвреден. Первый не гарантирует ничего для ROOT-строк, так как в Postgres `NULL != NULL` в unique-индексах — именно поэтому и добавлен `uk_folder_user_root`.

**[CONFIRMED]** ON DELETE CASCADE по `parent_id` означает: удаление ROOT в БД удалит всё дерево. Через API это недостижимо (ROOT удалить нельзя), но каскад срабатывает при удалении пользователя.

## 4. Соответствие entity ↔ migration

`ddl-auto: validate` проверяет **таблицы, колонки и их типы**, но **не проверяет** индексы, unique-индексы (кроме объявленных через `@UniqueConstraint`), FK, CHECK и default-значения. Отсюда следующие наблюдения:

| # | Расхождение | Тип | Влияние |
| --- | --- | --- | --- |
| 1 | `FileItem` объявляет `@Index(name="uk_file_item_user_folder_checksum", unique=true)` внутри `@Table(indexes=...)` — Hibernate это не валидирует, ограничение фактически создаётся только migration 14 | **[INCONSISTENCY]** | декоративно; реальное ограничение в БД есть |
| 2 | `@Index` в `FileItem` для `idx_file_item_user_captured_uploaded_id` перечисляет колонки без `DESC`, в БД индекс с `DESC` | **[INCONSISTENCY]** | косметическое |
| 3 | В сущностях не объявлен индекс `idx_file_item_user_folder_lower_original_name` (functional-индекс невозможно выразить в JPA) | **[INFERRED]** | норма |
| 4 | `User.email`/`User.password` без `@Column(nullable=false)`, в БД NOT NULL | **[INCONSISTENCY]** | косметическое |
| 5 | `RefreshToken.revoked` — примитив `boolean`, колонка nullable | **[INCONSISTENCY][RISK]** | `NULL` в колонке → ошибка маппинга |
| 6 | `RefreshToken` без `@Table` — имя выводится naming-стратегией в `refresh_token`, совпадает с миграцией | **[CONFIRMED]** | ок |
| 7 | `Folder`/`StoredObject` объявляют `@Index`, соответствующие миграциям 10 | **[CONFIRMED]** | ок |
| 8 | CHECK `ck_folder_not_self_parent` не отражён в сущности | **[INFERRED]** | норма |

## 6. Индексы под фактические запросы

Сопоставление реально выполняемых запросов и доступных индексов:

| Запрос (repository-метод) | Условие | Индекс | Оценка |
| --- | --- | --- | --- |
| `FileItemRepository.findAllByUserId(pageable)` | `user_id`, ORDER BY `captured_at desc, uploaded_at desc, id desc` | `idx_file_item_user_captured_uploaded_id` | **точное совпадение** |
| `findAllByUserIdAndFolderId(pageable)` | `user_id, folder_id` + та же сортировка | частично `idx_file_item_folder`; составного `(user_id, folder_id, captured_at…)` нет | **[RISK]** сортировка потребует отдельного шага |
| `findByIdAndUserId` | `id, user_id` | PK | ок |
| `findFirstByUserIdAndFolderIdAndChecksumOrderByIdAsc` | `user_id, folder_id, checksum` | `uk_file_item_user_folder_checksum` | **точное совпадение** |
| `findExistingChecksumsInFolder` | `user_id, folder_id, lower(checksum) IN (...)` | **[RISK]** `lower(checksum)` — функция по колонке, functional-индекса нет → индекс `uk_file_item_user_folder_checksum` не применим к `lower()` |
| `existsByUserIdAndFolderIdAndOriginalNameIgnoreCase` | `user_id, folder_id, lower(original_name)` | `idx_file_item_user_folder_lower_original_name` | **точное совпадение** |
| `findAllByStoredObjectId` | `stored_object_id` | `idx_file_item_stored_object` | ок |
| `existsByFolderId` | `folder_id` | `idx_file_item_folder` | ок |
| `findAllChecksumsAndOriginalFilenamesByUserId` | `user_id`, без limit | `idx_file_item_user_captured_uploaded_id` (префикс) | **[RISK]** полная выборка без пагинации |
| `FolderRepository.findRootByUserId` | `user_id, parent IS NULL, folder_type=ROOT` | `uk_folder_user_root` | **точное совпадение** |
| `findByUserIdAndParentIdAndFolderType` | `user_id, parent_id, folder_type` | `idx_folder_user_parent` / `idx_folder_user_type` | ок |
| `findChildrenByUserIdAndParentId` | `user_id, parent_id` ORDER BY `lower(name), id` | `idx_folder_user_parent` (сортировка отдельно) | приемлемо |
| `findByUserIdAndParentIdAndName` | `user_id, parent_id, lower(name)` | `uk_folder_user_parent_name` | **точное совпадение** |
| `existsByParentId` | `parent_id` | `idx_folder_user_parent` (не префикс!) | **[RISK]** `parent_id` — второй столбец, индекс неэффективен |
| `UserRepository.findByEmailIgnoreCase` | `email = LOWER(:email)` | `users_email_uindex` | ок (функция применяется к параметру, не к колонке) |
| `RefreshTokenRepository.findByToken` | `token` | **нет** | **[RISK] seq scan** |
| `findAllByUserNameAndRevoked` | `user_name, revoked` | `refresh_token_user (user_name)` | приемлемо |
| `EmailRequestRepository.findByCode` | `code` | `email_requests_code_unique` | ок |
| `countByUserAndTypeAndCreatedAtAfter` | `user_id, type, created_at` | **нет** | **[RISK]** (метод сейчас не вызывается) |

**[CONFIRMED][RISK]** Особо отмечу `findExistingChecksumsInFolder`: JPQL применяет `lower()` к колонке `f.checksum`. Так как сервис уже нормализует входные checksum в lowercase, а сервер всегда пишет checksum в lowercase (`DatatypeConverter.printHexBinary(...).toLowerCase()` в `FileUtils`), `lower()` по колонке избыточен, но лишает запрос возможности использовать `uk_file_item_user_folder_checksum`.

## 7. Транзакции

**[CONFIRMED]**

| Место | Механизм | Границы |
| --- | --- | --- |
| `FolderService` — все публичные методы | декларативный `@Transactional` (`org.springframework.transaction.annotation`) | метод целиком; `getChildren`/`getFolderForUser` — `readOnly = true` |
| `EmailRequestService.confirmEmail/confirmRegistration/resetPassword` | `@Transactional` (**`jakarta.transaction.Transactional`**, не Spring) | метод целиком; изменения применяются через dirty checking без явного `save()` |
| `FileItemService.createStoredObjectAndFileItem()` | программный `TransactionTemplate` | только `save(StoredObject)` + `save(FileItem)` |
| `FileItemService.createCopiedStoredObjectAndFileItem()` | программный `TransactionTemplate` | только записи в БД |
| `FileItemService.deleteFileForCurrentUser()` | программный `TransactionTemplate` | `deleteAll(FileItem)` + `flush()` + `delete(StoredObject)`; удаление файла с диска — **после** commit |
| `FileItemService.rename/move/copy(внешняя часть)/getUserFiles/getChecksumsForUser` | **транзакции нет** | каждый repository-вызов — своя транзакция |
| `UserService.*` | **транзакции нет** | `register()` делает `save(user)` и `save(emailRequest)` в **разных** транзакциях |
| `JwtService.*` | **транзакции нет** | |

**[CONFIRMED][RISK]** `UserService.register()` не транзакционен: если `generateEmailRequest()` упадёт после `userRepository.save(user)`, пользователь останется создан без кода активации и без возможности его перевыпустить (resend не реализован).

**[CONFIRMED][RISK]** `FileItemService.renameFileForCurrentUser()`: `ensureFileNameAvailable()` и `save()` выполняются в разных транзакциях, а БД-ограничения на `original_name` нет → два параллельных rename могут создать одинаковые имена в одной папке.

**[CONFIRMED]** `spring.jpa.open-in-view: false` — ленивая инициализация вне сервиса невозможна; поэтому `FileItemRepository` помечает все методы чтения `@EntityGraph(attributePaths = {"folder","folder.parent","storedObject","metadata"})`.

## 8. Целевые проверки

### 8.1. Duplicate handling

**[CONFIRMED]** Дубликат = `(user_id, folder_id, checksum)` на уровне `file_item`.

- Ограничение БД: `uk_file_item_user_folder_checksum` (migration 14).
- Проверка в приложении: `FileItemService.uploadFile()` (до записи) и `ensureChecksumAvailableInFolder()` (в `copy`).
- Гонка обрабатывается: `uploadFile()` ловит `DataIntegrityViolationException`, удаляет свой физический файл и возвращает уже существующий `FileItem` (строки 139–146).
- **[RISK]** `move` эту инварианту не проверяет — см. `16-known-gaps-and-risks.md`.

### 8.2. Checksum uniqueness

**[CONFIRMED]**

| Область | Уникален? |
| --- | --- |
| Глобально по всем пользователям | **нет** |
| В пределах пользователя | **нет** (было в migration 11, снято в 13) |
| В пределах `(user, folder)` для `file_item` | **да** |
| В пределах `stored_object` | **нет**, только неуникальный индекс |

Следствие: один и тот же файл, загруженный в 3 папки, займёт на диске 3 копии.

### 8.3. Filename / path uniqueness

**[CONFIRMED]**

- `file_item.original_name`: **уникальности в БД нет**. Есть functional-индекс `idx_file_item_user_folder_lower_original_name`, но он **не unique** — только ускоряет проверку в приложении.
- `stored_object.file_path + filename`: уникальности в БД нет; практически обеспечивается UUID в имени файла (`FilenameSanitizer.buildPhysicalFilename()`).
- Прежнее ограничение `uk_stored_object_user_storage_key` удалено в migration 11.

### 8.4. Отношение файл ↔ пользователь

**[CONFIRMED]** Пользователь фигурирует в трёх местах: `file_item.user_id`, `stored_object.user_id`, `folder.user_id`. Все три — независимые FK на `users`. Проверки целостности «`file_item.user_id` = `folder.user_id` = `stored_object.user_id`» в БД **нет**; она обеспечивается только кодом (все lookup по `id + userId`).

**[INFERRED][RISK]** Именно поэтому ветка «не владелец `StoredObject`» в `deleteFileForCurrentUser()` формально возможна на уровне схемы, хотя API её создать не позволяет.

### 8.5. Поведение при удалении пользователя

**[CONFIRMED]** Endpoint'а удаления пользователя нет. Если удалить строку напрямую в БД:

| Объект | Поведение |
| --- | --- |
| `user_roles` | CASCADE — удаляются |
| `email_requests` | CASCADE — удаляются |
| `folder` | CASCADE — удаляется всё дерево (плюс рекурсивный каскад по `parent_id`) |
| `file_item` | CASCADE по `user_id` |
| `stored_object` | CASCADE по `user_id` |
| `refresh_token` | **остаются** — FK нет |
| **Физические файлы на диске** | **остаются навсегда** — **[RISK]** ни триггера, ни job, ни кода очистки |

**[INFERRED]** Порядок разрешения каскадов: `file_item` ссылается на `folder` и `stored_object` без `ON DELETE`, но все три удаляются одним каскадом от `users`. PostgreSQL выполняет RI-действия рекурсивно, поэтому удаление должно пройти; тем не менее это **не проверено ни тестом, ни в коде**.

### 8.6. Поведение при удалении файла

**[CONFIRMED]** `FileItemService.deleteFileForCurrentUser()`:

```
если file.user.id != storedObject.user.id:
    удалить только этот FileItem  (физфайл и StoredObject не трогаются)
иначе (владелец):
    TRANSACTION {
        удалить ВСЕ FileItem, ссылающиеся на storedObject
        flush()
        удалить StoredObject
    }
    после commit: Files.deleteIfExists(path)   // ошибка только логируется
```

- `file_metadata` удаляется каскадом БД (`ON DELETE CASCADE`) и/или `orphanRemoval = true` на `@OneToOne`.
- **[CONFIRMED][RISK]** Если `Files.deleteIfExists()` упадёт, запись из БД уже удалена → **orphan-файл**, строка лога `ERROR` и никакого механизма повторной попытки.

### 8.7. Поведение при удалении папки

**[CONFIRMED]** Двойная защита: `FolderService.deleteFolder()` проверяет `existsByParentId` и `existsByFolderId` и бросает `FolderOperationException` (`400`); на уровне БД FK `file_item.folder_id` без `ON DELETE` даст RESTRICT.
