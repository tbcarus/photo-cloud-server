## 2. Что могло бы быть фоновым, но выполняется синхронно

**[CONFIRMED]**

| Операция | Где | Влияние на время ответа |
| --- | --- | --- |
| Отправка письма при регистрации | `UserService.register()` → `EmailService.sendEmail()` | SMTP-соединение с внешним сервером внутри HTTP-запроса; таймауты JavaMail не заданы → потенциально долгая блокировка |
| Отправка письма при запросе сброса пароля | `UserService.forgotPassword()` | то же |
| Рендеринг Thymeleaf-шаблона письма | `EmailService.sendEmail()` | незначительно |
| Извлечение EXIF-метаданных | `DrewFileMetadataExtractor.extract()` внутри upload | чтение файла с диска, парсинг |
| Определение MIME (Tika) | `FileContentDetector.detectMimeType()` внутри upload | чтение сигнатуры файла |
| Подсчёт SHA-256 | `FileUtils.writeAndCalculateSHA256()` | совмещён с записью потока — накладных расходов почти нет |
| Физическое копирование файла при `copy` | `Files.copy()` внутри HTTP-запроса | для 100 MiB — заметная задержка |
| Удаление физического файла | `Files.deleteIfExists()` после commit | быстро |

**[INFERRED][RISK]** Отправка письма — наиболее очевидный кандидат на вынос в фон: она уже толерантна к сбоям (исключение поглощается), но при недоступности SMTP держит поток Tomcat.

## 3. Отсутствующие обслуживающие задачи

**[CONFIRMED]** Ни одна из перечисленных ниже задач не реализована и не запланирована в коде:

| Задача | Зачем нужна | Текущее последствие отсутствия |
| --- | --- | --- |
| Очистка протухших `refresh_token` | таблица растёт монотонно | каждый login добавляет строку; удаления нет **никогда** |
| Очистка использованных/истёкших `email_requests` | то же | `EmailRequestService.delete()` — пустой метод |
| Очистка `storage.temp-dir` | брошенные `upload-*.tmp` при аварийном завершении | мусор накапливается бессрочно |
| Поиск orphan-файлов (файл есть, записи нет) | расхождение ФС ↔ БД | orphan-файлы не обнаруживаются (см. `07-file-storage.md` §10.1) |
| Поиск orphan-записей (запись есть, файла нет) | то же | обнаруживается только при попытке скачивания |
| Обработка корзины (`deletedAt` + TTL) | soft delete | колонка не используется |
| Генерация миниатюр | превью в клиенте | функции нет |
| Пересчёт/сверка checksum | контроль целостности | checksum после записи никогда не перепроверяется |
| Пересчёт занятого места / квоты | биллинг, лимиты | квот нет |
| Обновление статистики БД, VACUUM | эксплуатация PostgreSQL | на стороне СУБД, вне приложения |
| Ротация ключа подписи JWT | security | не поддерживается |
| Резервное копирование | эксплуатация | вне приложения, скриптов в репозитории нет |

## 4. Retry-механизмы

**[CONFIRMED]** Отсутствуют полностью — подробно в `10-errors-retries.md` §7.

Ни одной из следующих конструкций в проекте нет:

- Spring Retry (`@Retryable`, `RetryTemplate`) — зависимость не подключена;
- ручных циклов повтора;
- exponential backoff;
- dead letter queue;
- очереди отложенных операций (например, «удалить файл позже, если сейчас не получилось»);
- circuit breaker (Resilience4j и т.п.).

Единственные «повторы» в коде — разрешение конкурентных конфликтов через перехват `DataIntegrityViolationException` с повторным чтением (`FolderService.createRootRaceSafe()`, `FolderService.createSystemChildRaceSafe()`, `FileItemService.uploadFile()`). Это не retry-политика, а обработка гонки; повтора самой операции не происходит.

## 5. Единственная «фоновая» активность в процессе

**[CONFIRMED]** Формально в приложении работают только те фоновые потоки, которые создаются самими фреймворками и не относятся к бизнес-логике:

| Поток/пул | Кем создан | Назначение |
| --- | --- | --- |
| Tomcat NIO worker threads | Spring Boot / embedded Tomcat | обработка HTTP-запросов |
| HikariCP housekeeping | Hikari | обслуживание пула соединений |
| Liquibase (одноразово при старте) | Spring Boot | применение миграций |

**[CONFIRMED]** Liquibase — единственная операция, выполняющаяся автоматически без HTTP-запроса, и происходит она ровно один раз при старте контекста (`spring.liquibase.enabled: true`).

## 6. Ленивая инициализация как замена «джобам»

**[CONFIRMED]** То, что в других системах делалось бы фоновой подготовкой данных, здесь выполняется лениво по запросу:

| Что | Когда создаётся | Код |
| --- | --- | --- |
| `ROOT`-папка пользователя | при первом `GET /folders/root` или первом upload без `folderId` | `FolderService.getOrCreateRoot()` |
| Папка `Camera` | при первом upload IMAGE/VIDEO без `folderId` | `FolderService.getDefaultFolder()` |
| Папка `Files` | при первом upload прочих типов без `folderId` | там же |
| Каталоги хранилища | при первой записи файла в соответствующий шард | `Files.createDirectories()` |
| Каталог `tmp` | при первом upload | `FileItemService.createTempFile()` |

**[INFERRED]** Это разумная замена стартовой инициализации: состояние создаётся по факту необходимости, гонки обработаны через unique-ограничения БД.

## 7. Влияние на клиент

**[CONFIRMED]** Для Android-клиента важны следующие следствия отсутствия фоновой обработки:

1. **Все ответы синхронны.** Нет статусов «в обработке», нет polling'а, нет callback'ов/webhook'ов. Если `POST /files` вернул `200`, файл уже полностью сохранён и доступен для скачивания.
2. **Нет постобработки.** Миниатюры не появятся позже; метаданные извлечены в момент загрузки или не извлечены вовсе.
3. **Нет отложенной синхронизации на сервере.** Сервер ничего не «досчитывает» между запросами — клиент видит ровно то состояние, которое сам создал.
4. **Ретраи — целиком ответственность клиента.** Сервер не повторит ни отправку письма, ни удаление файла, ни неудавшуюся операцию.
5. **Ничего не «протухает» само.** Отозванные токены и использованные коды остаются в БД; сервер не выполняет уборку, которая могла бы изменить состояние между запросами клиента.
