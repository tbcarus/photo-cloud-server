# 02. Auth Contract (клиентская часть)

> Только то, что влияет на Android-клиент. Внутреннее устройство серверных security-классов опущено.

---

## 1. Модель в двух словах

Сервер **stateless**. Серверных сессий нет, cookie не выдаются. Всё состояние аутентификации на клиенте — это **две строки JWT**:

| Токен | Срок жизни | Хранится на сервере | Можно отозвать |
| --- | --- | --- | --- |
| **access token** | **20 минут** | нет | **нет** |
| **refresh token** | **7 дней** | да (строка в БД) | да (через logout) |

Оба — JWT, подписаны HMAC-SHA. Клиенту разбирать их **не требуется** и не рекомендуется: сервер не гарантирует стабильность внутренней структуры. Однако при необходимости внутри access token есть `sub` (email), `roles`, `token_type: "ACCESS"`, `iat`, `exp`.

---

## 2. Login

**`POST /api/v1/auth/login`** — публичный.

```json
{"email": "user@example.com", "password": "pass1"}
```

Валидация: email — формат; password — **4–20 символов**.

**`200`:**
```json
{"accessToken": "<jwt>", "refreshToken": "<jwt>"}
```

**Что клиент должен знать:**

1. `401 INVALID_CREDENTIALS` возвращается **одинаково** в четырёх разных случаях: email не найден, пароль неверен, аккаунт не подтверждён (`enabled=false`), аккаунт заблокирован (`banned=true`). **Различить их невозможно.** Сообщение пользователю должно быть общим («неверный email или пароль»), но стоит добавить подсказку «если вы недавно регистрировались — подтвердите email».
2. Каждый login создаёт **новую** пару токенов и новую серверную запись. Предыдущие refresh-токены **не отзываются** — повторный login с другого устройства не выкинет первое.
3. Ограничения на число сессий нет.
4. Валидация `@Size(max = 20)` применяется и к login: пароль длиннее 20 символов будет отклонён с `400` **до** проверки — клиенту не нужно ограничивать длину при вводе жёстче, но нужно быть готовым к `400 VALIDATION_ERROR` на поле `password`.

---

## 3. Использование access token

Заголовок на **каждом** защищённом запросе:

```
Authorization: Bearer <accessToken>
```

Префикс `Bearer ` (с пробелом) обязателен и регистрозависим — сервер проверяет `startsWith("Bearer ")`.

**Что происходит при разных проблемах с токеном:**

| Ситуация | Ответ |
| --- | --- |
| Заголовка нет | `401 UNAUTHORIZED` |
| Токен истёк | `401 UNAUTHORIZED` |
| Токен повреждён/подделан | `401 UNAUTHORIZED` |
| Прислан refresh token вместо access | `401 UNAUTHORIZED` |
| Пользователь удалён на сервере | **`500`** (дефект сервера) |

**Важно:** все `401` неотличимы — тело всегда одно и то же:
```json
{"id":"<uuid>","code":"UNAUTHORIZED",
 "message":"Unauthorized: access token expired or invalid","fieldErrors":null}
```

Клиент не может по ответу понять, истёк токен или он невалиден. **Практический вывод:** на любой `401` пробовать refresh; если refresh тоже не прошёл — re-login.

---

## 4. Refresh

**`POST /api/v1/auth/refresh-token`** — **публичный**, access token в заголовке **не нужен**.

```json
{"refreshToken": "<jwt>"}
```

**`200`:**
```json
{"accessToken": "<новый jwt>"}
```

**Ключевые свойства:**

1. **Возвращается только access token.** Refresh token **не ротируется** — клиент продолжает использовать тот же самый.
2. Новый refresh token можно получить **только через повторный login**.
3. Операция **полностью идемпотентна** — не изменяет ничего на сервере, можно вызывать повторно.
4. Срок refresh не продлевается: ровно через 7 дней после login потребуется полный re-login, сколько бы раз клиент ни обновлял access.

**Ошибки refresh:**

| Статус | `code` | Значение | Действие клиента |
| --- | --- | --- | --- |
| `400` | `VALIDATION_ERROR` | пустой `refreshToken` | ошибка клиента |
| `401` | `INVALID_REFRESH_TOKEN` | токена нет в БД / истёк / повреждён / не того типа | **полный re-login** |
| `403` | `REFRESH_TOKEN_REVOKED` | был выполнен logout | **полный re-login** |

Оба терминальных случая требуют одного и того же — повторного входа. Различать их клиенту нужно только для аналитики.

---

## 5. Logout

### `POST /api/v1/auth/logout` — выход на текущем устройстве

**Требует Bearer access token** + тело:
```json
{"refreshToken": "<текущий refresh>"}
```

**`200`:** `{"message":"Logged out successfully"}`

> ⚠️ **Самая важная деталь для клиента:** logout требует **валидный access token**. Если пользователь не пользовался приложением дольше 20 минут, access истёк, и logout вернёт `401`.
>
> **Правильная последовательность выхода:**
> ```
> 1. POST /auth/refresh-token  (получить свежий access)
> 2. POST /auth/logout         (с этим access + refresh в теле)
> 3. очистить локальное хранилище токенов
> ```
> Если шаг 1 или 2 не удался — всё равно выполнить шаг 3. Токены на сервере протухнут сами.

### `POST /api/v1/auth/logout-all` — выход на всех устройствах
Требует Bearer. Тела нет. `200`: `{"message":"All logged out successfully"}`

### `POST /api/v1/auth/logout-others` — выход везде, кроме текущего
Требует Bearer + тело с **текущим** refresh token (тот, который нужно **сохранить**):
```json
{"refreshToken": "<текущий refresh>"}
```
При ошибке (`403`/`404`) **ничего не отзывается** — операция безопасна.

**Ошибки logout-операций:**

| Статус | `code` | Значение |
| --- | --- | --- |
| `400` | `VALIDATION_ERROR` | пустой `refreshToken` |
| `401` | `UNAUTHORIZED` | нет/истёк access token |
| `403` | `REFRESH_TOKEN_OWNERSHIP_ERROR` | токен принадлежит другому пользователю |
| `404` | `REFRESH_TOKEN_NOT_FOUND` | токена нет в БД |

**`404` на logout можно считать успехом** — если токена нет на сервере, цель достигнута.

---

## 6. Что происходит после logout

| Токен | Состояние |
| --- | --- |
| refresh token | **отозван** — refresh даст `403`, повторное использование невозможно |
| access token | **остаётся валидным до 20 минут** — сервер его не отзывает |

**Практический вывод:** сервер не может «выкинуть» клиента мгновенно. Клиент **обязан** удалить оба токена локально при logout — на серверную инвалидацию access token полагаться нельзя.

---

## 7. Поведение при смене пароля

> ⚠️ **Смена пароля НЕ отзывает refresh-токены.**

После успешного `POST /auth/password/reset/confirm` все существующие сессии (на всех устройствах) продолжают работать до истечения 7 дней или явного logout.

**Следствие для клиента:**
- после смены пароля **не нужно** принудительно перелогинивать пользователя — старый токен продолжит работать;
- но если продукт хочет поведение «смена пароля завершает все сессии», клиент должен сам вызвать `POST /auth/logout-all` **до** сброса (пока у него ещё есть валидный access token) — сервер этого не сделает.

## 8. Регистрация и активация — с точки зрения клиента

```
POST /auth/register {email, password}       → 201 {"message":"Email was sent"}
    (аккаунт создан, но enabled = false — войти нельзя)
        ↓
пользователь открывает ссылку из письма
GET /auth/register/confirm?code=<uuid>      → 200 text/plain "User ... was verified"
        ↓
POST /auth/login                            → 200 {accessToken, refreshToken}
```

**Ограничения:**

1. Между регистрацией и подтверждением **login возвращает `401 INVALID_CREDENTIALS`** — неотличимо от неверного пароля. Клиенту стоит после успешной регистрации явно показать экран «подтвердите email».
2. **Повторная отправка письма невозможна** — `POST /auth/register/resend` возвращает `501`. Регистрация тем же email даст `409`. Пользователь, потерявший письмо, попадает в тупик — сообщите ему об этом заранее.
3. Код активации живёт **3 дня**.
4. `GET /auth/register/confirm` возвращает `text/plain`, а не JSON — если клиент перехватывает эту ссылку deep link'ом, парсить как JSON нельзя.
5. Сервер возвращает `201` даже если письмо фактически не отправилось.

## 9. Восстановление пароля — с точки зрения клиента

```
POST /auth/password/reset/request?email=<email>   → 200 {"message":"Email was sent"}
        (email передаётся в QUERY, не в теле!)
        ↓
пользователь получает письмо со ссылкой на /api/v1/auth/password/reset/page?code=<uuid>
        ⚠ этот endpoint возвращает 501 — рабочей веб-страницы НЕТ
        ↓
клиент должен получить code (перехватить deep link или попросить скопировать)
        ↓
POST /auth/password/reset/confirm {password, code}  → 200 {"message":"Password was reset"}
```

**Ограничения:**
- несуществующий email даёт `400 BAD_REQUEST` — клиент может это использовать, но учтите, что это раскрытие информации;
- rate limiting отсутствует — не полагайтесь на серверную защиту от спама, ограничивайте частоту на клиенте;
- код живёт 3 дня; после успешного сброса **все** активные коды сброса становятся недействительными.

## 10. Что клиент должен хранить

| Что | Обязательно | Где | Комментарий |
| --- | --- | --- | --- |
| `accessToken` | ✅ | защищённое хранилище (EncryptedSharedPreferences / Keystore) | живёт 20 минут; отправляется в каждом запросе |
| `refreshToken` | ✅ | защищённое хранилище | живёт 7 дней; **не меняется** после refresh |
| email пользователя | желательно | обычное хранилище | для подстановки в форму входа |
| время получения access token | желательно | обычное хранилище | позволяет обновлять токен проактивно, не дожидаясь `401` |
| время получения refresh token | желательно | обычное хранилище | позволяет заранее предупредить о необходимости re-login |
| `id` пользователя | опционально | из `GET /profile` | сервер не требует его в запросах |

**Что хранить НЕ нужно:**
- пароль (сервер не предоставляет операций, требующих его повторно, кроме login);
- роли (сервер их не проверяет);
- срок жизни токенов как константу — лучше вычислять из `exp` в JWT либо вести время получения.

## 11. Рекомендуемая стратегия работы с токенами

**[Оценочное — не описание сервера, а вывод из его контракта]**

```
Запрос к защищённому endpoint'у
    ↓
401?
    ├── нет  → готово
    └── да   → POST /auth/refresh-token
                  ├── 200 → сохранить новый accessToken → ПОВТОРИТЬ исходный запрос ОДИН раз
                  ├── 401 → полный re-login
                  ├── 403 → полный re-login (был logout)
                  └── сеть → повторить позже, состояние не менять
```

Важные детали:

- **Повторять исходный запрос ровно один раз.** Если после успешного refresh снова пришёл `401` — это не проблема токена.
- **Refresh должен быть однопоточным.** При параллельных запросах несколько `401` придут одновременно; все они должны ждать одного refresh, а не запускать свой. Сервер выдержит и параллельные (операция идемпотентна), но клиент получит несколько разных access token'ов и лишний трафик.
- **Upload безопасно повторять после refresh** — он идемпотентен в пределах папки (см. `05-sync-upload-contract.md`).
- **`DELETE` повторять после refresh опасно**: если первый запрос успел выполниться, повтор вернёт `404`. Трактуйте `404` на повторе delete как успех.
- Проактивное обновление (за 1–2 минуты до `exp`) сокращает число `401` и особенно полезно перед длинной загрузкой: access может истечь **во время** передачи большого файла.

## 12. Что сервер НЕ предоставляет

| Возможность | Статус |
| --- | --- |
| Отзыв access token | ❌ невозможно (не хранится) |
| Ротация refresh token | ❌ не реализована |
| Продление срока refresh | ❌ нет |
| Список активных сессий/устройств | ❌ нет |
| Идентификация устройства | ❌ модели `Device` нет |
| Уведомление о входе с нового устройства | ❌ нет |
| Смена пароля со старым паролем (без email) | ❌ нет |
| Смена email | ❌ нет |
| Удаление аккаунта | ❌ нет |
| MFA / биометрия на сервере | ❌ нет |
| OAuth / вход через провайдера | ❌ нет |
| Rate limiting | ❌ нет — клиент должен ограничивать себя сам |
| Проверка `banned` после выдачи токена | ❌ нет — заблокированный пользователь работает до истечения токенов |
