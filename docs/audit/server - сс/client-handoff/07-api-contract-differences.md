# 07. API Contract Differences

> Расхождения между **документацией проекта** и **фактическим поведением сервера**.
>
> **Важное замечание.** Файла `api-contract.md` в проекте нет. Вместо него — четыре тематических документа: `docs/api-user-contract.md`, `docs/api-folder-contract.md`, `docs/api-file-contract.md`, `docs/api-checksum-sync-contract.md`, плюс обзорный `docs/application-overview.md` и `docs/http-tests/`.
>
> **Общая оценка качества документации: высокая.** Она подробна, актуальна по большинству пунктов и написана по коду. Расхождений мало, но два из них могут привести к неверным решениям в клиенте.

## 2. Два расхождения, критичных для клиента

### #1 — `move` возвращает `500` вместо `409`

**Что говорит документация.** `api-file-contract.md` перечисляет для `POST /files/{id}/move` только `400`, `404` и `409`.

**Что делает сервер.** Проверяется только конфликт **имени**. Конфликт **checksum** (в целевой папке уже есть файл с тем же содержимым) не проверяется — срабатывает ограничение БД `UNIQUE (user_id, folder_id, checksum)`, и глобальный обработчик превращает его в `500 DATABASE_CONSTRAINT_VIOLATION`.

**Почему это опасно для клиента.** Стандартная политика «retry на 5xx, не retry на 4xx» приведёт к бесконечным повторам запроса, который **никогда** не выполнится успешно.

**Что делать клиенту.**
1. Трактовать `500` с `code = "DATABASE_CONSTRAINT_VIOLATION"` как **терминальный конфликт**, а не как временный сбой.
2. Перед `move` проверять целевую папку через `POST /files/checksums/exists` — это единственный надёжный способ избежать `500`.

Наличие поля `code` в теле — надёжный признак: у необработанных `500` (реальных сбоев) его нет вовсе.

### #2 — Восстановление пароля не работает через браузер

**Что говорит документация.** `api-user-contract.md` помечает `/auth/password/reset/page` как «зарезервированный endpoint» в общем списке нереализованных.

**Что делает сервер.** Письмо сброса пароля формирует ссылку **именно на этот адрес**. Пользователь, перешедший по ней, получает `501`.

**Почему это важно для клиента.** Рабочий сценарий восстановления пароля возможен **только через приложение**: клиент должен либо перехватывать ссылку deep link'ом и извлекать `code`, либо инструктировать пользователя скопировать `code` из адресной строки и вставить в приложение. Полагаться на «пользователь перейдёт по ссылке и всё сработает» нельзя.

## 4. Что документация описывает лучше, чем можно было ожидать

Отмечу отдельно — эти места **не** расходятся с кодом и заслуживают доверия:

1. Модель дедупликации `user + folder + checksum`, включая обработку гонки и обоснование, почему `copy` не использует dedup.
2. Поведение `CAMERA` (разрешены одинаковые имена) — описано и покрыто тестами.
3. Отсутствие отзыва токенов при смене пароля — **явно** предупреждено в документации.
4. Использование `404` вместо `403` для чужих объектов — описано с обоснованием.
5. Логика upload pipeline по шагам — соответствует коду вплоть до порядка операций.
6. Семантика `checksums/exists` (нормализация, порядок, batch-лимит) — точна.
7. Списки TODO в контрактах честно перечисляют нереализованное (sharing, soft delete, link-existing, device model).

## 5. Рекомендация аудитору Android-клиента

**Порядок доверия к источникам при анализе клиента:**

1. **`docs/audit/server/client-handoff/01-api-contract-effective.md`** (восстановлен по коду) — высший приоритет;
2. `docs/api-*-contract.md` — надёжны, с учётом расхождений #1–#3 из таблицы выше;
3. `docs/application-overview.md` — надёжен;
4. `docs/http-tests/*` — только как примеры вызовов, **не** как перечень возможностей;
5. `README.md`, `README-description.md`, `TODO.txt` — **не использовать** как описание API.

**Если в клиенте обнаружится код, ориентированный на:**

| Ожидание клиента | Реальность сервера |
| --- | --- |
| `201` при создании папки/загрузке файла | сервер возвращает `200` |
| retry на любой `500` | `DATABASE_CONSTRAINT_VIOLATION` терминален |
| ротацию refresh token | сервер возвращает только новый access |
| глобальную дедупликацию по checksum | дедупликация только в пределах папки |
| `deletedAt` для корзины | всегда `null` |
| `durationSec` для видео | всегда `null` |
| Range-запросы при скачивании | не поддерживаются |
| resumable upload | не поддерживается |
| ETag / `If-None-Match` | не выставляются |
| web-страницу сброса пароля | `501` |
| resend письма активации | `501` |
| редактирование профиля / настройки | `501` |
| единый формат ошибок для всех ответов | три разных формата |
| таймзону в датах | `LocalDateTime` без смещения |

— это **ошибка в клиенте или устаревшее ожидание**, а не дефект сервера.
