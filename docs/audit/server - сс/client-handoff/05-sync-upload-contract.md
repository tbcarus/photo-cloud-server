# 05. Sync & Upload Contract (серверная сторона)

> Этот документ позволяет анализировать логику синхронизации Android-клиента **без чтения серверного репозитория**.
> Всё описанное подтверждено кодом `FileItemService`, `ChecksumSyncService`, `FolderService` и ограничениями БД.

---

## 1. Главное правило системы

> **Дубликат = один и тот же `checksum` в одной и той же папке одного пользователя.**
>
> Формально: уникальное ограничение БД `UNIQUE (user_id, folder_id, checksum)` на таблице логических записей.

Из этого следует всё остальное:

| Утверждение | Верно? |
| --- | --- |
| Один файл нельзя загрузить в одну папку дважды | ✅ — вторая попытка вернёт существующую запись |
| Один файл **можно** загрузить в две разные папки | ✅ — это создаст **две независимые записи и две физические копии** |
| Одинаковый checksum у разных пользователей — конфликт | ❌ — полностью независимы |
| Имя файла участвует в определении дубликата | ❌ — только `checksum` |
| Сервер экономит место при загрузке одного файла в N папок | ❌ — N копий на диске |

## 2. Как определить, что файл уже есть на сервере

Три способа, в порядке предпочтительности:

### Способ 1 (рекомендуемый): `POST /api/v1/files/checksums/exists`

Batch-проверка перед загрузкой.

```http
POST /api/v1/files/checksums/exists
Authorization: Bearer <accessToken>
Content-Type: application/json

{
  "folderId": 123,
  "checksums": ["3f8a...", "b71c...", "..."]
}
```

**Ответ `200`:**
```json
{"existing": ["3f8a..."], "missing": ["b71c..."]}
```

| Свойство | Значение |
| --- | --- |
| `folderId` | **обязателен** — проверка всегда в контексте конкретной папки |
| Максимум элементов | **500** за запрос |
| Формат элемента | ровно 64 hex-символа, любой регистр на входе |
| Ответ | всегда lowercase |
| Порядок | соответствует порядку первого появления во входном списке |
| Дубликаты входа | схлопываются автоматически |
| Побочные эффекты | **нет** — endpoint read-only, записей не создаёт |
| Идемпотентность | ✅ полная |

**Ограничение семантики:** ответ говорит только «есть/нет **в этой папке**». Он **не сообщает**, есть ли такой checksum в других папках пользователя.

### Способ 2: `GET /api/v1/files/checksums`

Полный список `{id, originalFilename, checksum}` всех файлов пользователя.

⚠️ **Без пагинации и без `folderId`.** Пригоден только для первичной сверки на небольшой библиотеке. По ответу **невозможно** определить, в какой папке лежит файл — поле `folderId` отсутствует.

### Способ 3: `GET /api/v1/files?folderId=X&page=&size=`

Постраничный обход с полными `FileItemDto` (включая `checksum` и `folderId`). Тяжелее, но даёт `id` и полную карточку — нужен для построения локального индекса.

## 3. Когда клиенту нужен checksum

**Всегда, если нужна проверка перед загрузкой.**

| Ситуация | Нужен checksum? |
| --- | --- |
| Pre-check `checksums/exists` | ✅ клиент обязан посчитать сам |
| Собственно загрузка (`POST /files`) | ❌ **сервер checksum не принимает** — параметра нет |
| Сопоставление локального файла с серверной записью | ✅ |
| Обнаружение изменения файла на устройстве | ✅ |

**Алгоритм:** SHA-256 содержимого файла, hex-представление. Сервер использует именно SHA-256 и хранит его в lowercase. При отправке в `checksums/exists` регистр не важен, но лучше сразу считать в lowercase.

⚠️ **checksum считается только по содержимому.** Изменение имени файла на устройстве checksum не меняет. Любое изменение содержимого (даже поворот фото средствами галереи) даёт **новый** checksum и, следовательно, новый файл с точки зрения сервера.

## 4. Duplicate detection: полная матрица

| Что загружаем | Куда | Результат на сервере | HTTP | Что вернётся |
| --- | --- | --- | --- | --- |
| Новые байты | новая папка | создан новый файл | `200` | новый `FileItemDto` |
| **Те же байты** | **та же папка** | **ничего не создано** | `200` | **существующий `FileItemDto` (прежний `id`)** |
| Те же байты | **другая** папка | создан новый файл + новая физическая копия | `200` | новый `FileItemDto` с новым `id` |
| Те же байты, другое имя | та же папка | ничего не создано | `200` | существующий `FileItemDto` **со старым именем** |
| Другие байты, то же имя | папка ≠ `CAMERA` | ничего не создано | **`409`** | `CONFLICT` — «File with this name already exists in folder» |
| Другие байты, то же имя | папка = `CAMERA` | создан новый файл | `200` | новый `FileItemDto`; имена дублируются |
| Те же байты, параллельно из двух потоков | одна папка | создан один файл | `200` (обоим) | обоим — **один и тот же** `FileItemDto` |

> **Ключевой вывод:** дубликат **не является ошибкой**. Сервер отвечает `200`, а не `409`. Отличить «загрузил новый» от «уже был» можно только по `id`: если он уже есть в локальном индексе — это был дубль.

## 5. Upload: контракт запроса

```http
POST /api/v1/files/upload
Authorization: Bearer <accessToken>
Content-Type: multipart/form-data; boundary=...

--boundary
Content-Disposition: form-data; name="file"; filename="IMG_20260609_202840.jpg"
Content-Type: image/jpeg          ← ИГНОРИРУЕТСЯ сервером

<байты файла>
--boundary
Content-Disposition: form-data; name="folderId"

123
--boundary--
```

| Параметр | Обязателен | Комментарий |
| --- | --- | --- |
| `file` | ✅ | часть multipart; при отсутствии — `400` |
| `folderId` | ❌ | параметр формы; при отсутствии сервер выбирает папку по типу |

**`POST /api/v1/files` и `POST /api/v1/files/upload` — полностью идентичны.** Первый помечен в коде как «сохранён для совместимости»; для нового кода предпочтительнее `/upload`.

**Что сервер делает с файлом:**

1. Проверяет, что файл не пустой.
2. Пишет поток во временный файл, **одновременно** считая SHA-256 и размер.
3. Отбрасывает файл при превышении лимита (потоково, не дожидаясь конца передачи).
4. Определяет MIME **по содержимому** (Apache Tika) — заголовок части игнорируется.
5. Выводит `fileType` из MIME.
6. Извлекает EXIF (только для `image/*`).
7. Определяет целевую папку.
8. **Проверяет дубликат по `user + folder + checksum`** — при совпадении удаляет временный файл и возвращает существующую запись.
9. Проверяет конфликт имени (пропускается для `CAMERA`).
10. Атомарно переносит файл в постоянное место.
11. Записывает в БД в транзакции.

## 6. Выбор папки при загрузке

**С `folderId`:** сервер проверяет, что папка существует и принадлежит пользователю. Чужая или несуществующая → **`404`**.

**Без `folderId`:**

| `fileType` (выведенный из MIME) | Папка по умолчанию |
| --- | --- |
| `IMAGE`, `VIDEO` | `Camera` |
| `AUDIO`, `DOCUMENT`, `ARCHIVE`, `OTHER` | `Files` |

Обе папки — прямые потомки `ROOT`, создаются **автоматически при первой загрузке** соответствующего типа. Отдельно создавать их не нужно и невозможно (имена `Camera` и `Files` зарезервированы в `ROOT`).

⚠️ **Важно:** без `folderId` клиент **не знает заранее**, куда попадёт файл — это зависит от MIME, определённого сервером. Для предсказуемой синхронизации **всегда передавайте `folderId` явно**: иначе pre-check по одной папке и фактическая загрузка в другую разойдутся.

⚠️ **`CAMERA` — особая папка:** проверка уникальности имени в ней **отключена**. Это удобно для фото с телефона (`IMG_0001.jpg` может встречаться многократно), но означает, что имя файла в `CAMERA` **не является идентификатором**.

## 7. Подтверждение загрузки

**[CONFIRMED]** Отдельного шага подтверждения (commit/finalize) **нет**. Протокол одношаговый:

```
POST /files/upload  →  200 + FileItemDto
```

Ответ `200` означает, что:
- байты полностью записаны на диск;
- запись в БД зафиксирована (транзакция закоммичена);
- файл немедленно доступен через `GET /files/{id}/download`.

Промежуточных состояний («загружается», «обрабатывается») **не существует** — ни в API, ни в модели данных. Постобработки после ответа тоже нет.

## 8. Идемпотентность и повторная загрузка

> ✅ **Upload идемпотентен в пределах папки. Повторять его после сбоя сети безопасно.**

Обоснование: повторная загрузка тех же байтов в ту же папку вернёт существующую запись; ограничение БД гарантирует, что дубликат не будет создан даже при гонке.

**Условие идемпотентности:** повторять нужно **с тем же `folderId`**. Повтор с другим `folderId` создаст второй файл — это by design, а не защита от него.

**Сценарии сбоя и что делать:**

| Сценарий | Состояние сервера | Действие клиента |
| --- | --- | --- |
| Обрыв во время передачи тела | ничего не создано, временный файл удалён | ✅ повторить |
| Таймаут, ответ не получен | **неизвестно** — файл мог сохраниться | ✅ повторить: вернётся существующая запись или создастся новая |
| `500` без `code` | вероятно, ничего не создано (сервер откатывает файл при сбое БД) | ✅ повторить с backoff |
| `413` | ничего не создано | ❌ **никогда** не повторять |
| `409` (имя) | ничего не создано | ⚠️ повторить только с другим именем |
| `404` (папка) | ничего не создано | ❌ пересинхронизировать дерево папок |
| `401` | ничего не создано | ✅ обновить access token и повторить |

## 9. Частичная загрузка и обрыв сети

> ❌ **Chunked / resumable upload не поддерживается.**

| Возможность | Статус |
| --- | --- |
| Загрузка по частям (`Content-Range`) | ❌ нет |
| Возобновление прерванной загрузки | ❌ нет |
| Session-based upload (`init` → `chunk` → `commit`) | ❌ нет |
| `Idempotency-Key` | ❌ нет |
| Промежуточные состояния на сервере | ❌ нет |

**Что делает сервер при обрыве:** временный файл удаляется, в БД ничего не создаётся. Никаких следов незавершённой загрузки не остаётся.

**Что это значит для клиента:** любая прерванная загрузка начинается **с нуля**. Для файла 100 MiB на нестабильной сети это может оказаться существенным ограничением — учитывайте это при проектировании очереди (например, загружать крупные файлы только на Wi-Fi).

**Аналогично для скачивания:** HTTP Range не поддерживается — прерванная загрузка файла на устройство тоже начинается заново.

## 10. Ограничения размера

| Лимит | Значение | Что происходит при превышении |
| --- | --- | --- |
| `multipart max-file-size` | **110 MB** | `413 FILE_TOO_LARGE` — «Multipart request exceeds configured limit» |
| `multipart max-request-size` | **110 MB** | то же |
| Лимит стриминга | **104 857 600 байт** (100 MiB) | `413 FILE_TOO_LARGE` — «File size exceeds limit: 104857600 bytes» |

**Практическая граница — 100 MiB (104 857 600 байт).** Проверка потоковая: сервер прерывает приём, как только счётчик превысил лимит, — не дожидаясь конца передачи.

**Отсутствующие ограничения:**

| Ограничение | Есть? |
| --- | --- |
| Квота на общий объём пользователя | ❌ нет |
| Ограничение количества файлов | ❌ нет |
| Ограничение типов файлов (whitelist MIME) | ❌ нет — принимается что угодно |
| Rate limiting на загрузку | ❌ нет |
| Ограничение количества параллельных загрузок | ❌ нет |

## 11. Рекомендуемый алгоритм синхронизации

**[Оценочное — вывод из контракта, а не описание сервера]**

```
0. LOGIN
   POST /auth/login → сохранить accessToken + refreshToken

1. ПОЛУЧИТЬ КОРЕНЬ И ДЕРЕВО
   GET /folders/root            → rootId
   GET /folders/{rootId}/children → найти Camera / Files / пользовательские папки
   (запомнить targetFolderId для автозагрузки — обычно Camera)

2. ПОСТРОИТЬ ЛОКАЛЬНЫЙ ИНДЕКС
   для каждого локального файла: посчитать SHA-256, сохранить в локальную БД

3. PRE-CHECK ПАЧКАМИ
   разбить список checksum на батчи <= 500
   для каждого батча:
       POST /files/checksums/exists {folderId: targetFolderId, checksums: [...]}
       existing → пометить локально как «уже на сервере»
       missing  → поставить в очередь загрузки

4. ЗАГРУЗКА ПО ОЧЕРЕДИ
   для каждого файла из очереди:
       POST /files/upload (file, folderId = targetFolderId)
       200 → сохранить локально id, folderId, uploadedAt, capturedAt
             (если id уже есть в индексе — это был дубль, не ошибка)
       401 → refresh → повторить один раз
       409 → конфликт имени: переименовать (вне CAMERA) и повторить
       413 → пометить как «слишком большой», больше не пытаться
       404 → папка исчезла: вернуться к шагу 1
       500/сеть → backoff, повторить позже (upload идемпотентен)

5. ОБРАТНАЯ СИНХРОНИЗАЦИЯ (файлы, появившиеся на сервере)
   GET /files?folderId=...&page=N&size=M — постранично
   сравнить checksum с локальным индексом
   ⚠ delta-sync нет: приходится обходить список целиком
```

**Ключевые замечания к алгоритму:**

1. **Всегда передавайте `folderId`** и в pre-check, и в upload — иначе они разойдутся.
2. **Pre-check не даёт гарантий на момент загрузки.** Между шагами 3 и 4 состояние может измениться. Это не проблема: upload идемпотентен и сам обработает дубль.
3. **Pre-check — оптимизация, а не необходимость.** Можно грузить всё подряд: сервер вернёт `200` с существующей записью. Pre-check экономит трафик, а не корректность.
4. **`checksums/exists` привязан к одной папке.** Для синхронизации нескольких папок нужен отдельный вызов на каждую.
5. **Обратная синхронизация дорогая.** Нет ни `modifiedSince`, ни курсора, ни push — только полный постраничный обход.

## 12. Что сервер НЕ предоставляет для синхронизации

| Возможность | Статус | Последствие для клиента |
| --- | --- | --- |
| Delta-sync (изменения с момента X) | ❌ нет | полный обход при каждой сверке |
| Курсорная пагинация | ❌ нет | offset-based; при изменениях страницы «едут» |
| Push / WebSocket / long polling | ❌ нет | изменения с другого устройства обнаруживаются только опросом |
| Link-existing (создать запись без передачи байтов) | ❌ нет | копирование файла в другую папку требует **либо** повторной загрузки байтов, **либо** `POST /files/{id}/copy` (сервер копирует сам) |
| Batch upload (несколько файлов за запрос) | ❌ нет | по одному HTTP-запросу на файл |
| Модель устройства | ❌ нет | сервер не различает устройства |
| Состояние синхронизации на сервере | ❌ нет | клиент — единственный владелец этого состояния |
| Уведомление об удалении на сервере | ❌ нет | обнаруживается по исчезновению из списка или по `404` |
| Корзина | ❌ нет | удаление необратимо, `deletedAt` всегда `null` |
| Расширенный ответ pre-check (`id`, `size`, `capturedAt`) | ❌ нет | после pre-check `id` неизвестен — нужен `GET /files` |
| Проверка целостности (сверка checksum на сервере) | ❌ нет | «битые» записи обнаруживаются только при скачивании (`404`) |

## 13. Копирование между папками без повторной загрузки

Если клиенту нужно поместить уже загруженный файл в **другую** папку, есть два варианта:

| Вариант | Как | Трафик | Результат |
| --- | --- | --- | --- |
| `POST /files/{id}/copy` с `targetFolderId` | сервер сам копирует байты | **байты не передаются** | новый `id`, новая физическая копия на сервере |
| `POST /files/{id}/move` с `targetFolderId` | сервер меняет только запись | нет | **тот же `id`**, файл исчезает из исходной папки |

⚠️ Оба варианта имеют ограничения:
- `copy` **в ту же папку всегда даёт `409`** (checksum уже присутствует);
- `move` в папку, где уже есть файл с тем же checksum, возвращает **`500 DATABASE_CONSTRAINT_VIOLATION`** — известный дефект сервера; повторять бесполезно.

**Рекомендация клиенту:** перед `move` проверять целевую папку через `checksums/exists` — это единственный способ избежать `500`.

## 14. Что считать «файл синхронизирован»

**[Оценочное]** Надёжный локальный признак:

```
файл синхронизирован ⟺ существует серверная запись
                        с ТЕМ ЖЕ checksum
                        в ЦЕЛЕВОЙ folderId
```

**Ненадёжные признаки — не использовать:**

| Признак | Почему ненадёжен |
| --- | --- |
| Совпадение имени файла | в `CAMERA` имена повторяются; `originalFilename` меняется через rename |
| Совпадение размера | коллизии вероятны |
| `capturedAt` | для видео всегда равен `uploadedAt` |
| Наличие checksum **где-либо** на сервере | тот же checksum в другой папке — **не** синхронизация целевой папки |
| `deletedAt` | всегда `null` |
| Локальный флаг «загружен» без проверки `id` | при переустановке приложения теряется |
