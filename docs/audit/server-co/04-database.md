## Транзакции, дубли и удаление

[CONFIRMED] FileItemService upload/copy: Files move/copy → TransactionTemplate(save StoredObject + FileItem + cascade metadata) → DTO. Ошибка DB компенсируется удалением final file; folder default создаётся отдельной @Transactional операцией. Rename/move используют repository.save без общей сервисной транзакции вокруг предварительных чтений.

[CONFIRMED] Owner delete: transaction delete всех FileItem для SO, flush, delete SO → commit → Files.deleteIfExists. Nonowner delete: только FileItem. SQL cascade metadata. API folder delete разрешает только empty USER; физический SQL parent cascade сам по себе не выполняет файловую очистку и может быть ограничен file_item FK.

[CONFIRMED] User deletion API нет. SQL users cascade охватывает roles/email/folders/file_items/stored_objects, но не refresh_token и не файловую систему. При искусственных cross-user ссылках некаскадный FK на SO/folder может препятствовать удалению. Утверждать «удаление аккаунта всё чистит» нельзя.

[CONFIRMED] Email confirm/reset @Transactional: изменения managed User/EmailRequest фиксируются dirty checking. UserService.register/login/forgotPassword не имеют общей транзакции; несколько repository writes и SMTP независимы. Bulk revoke сохраняется saveAll, без revokedAt.

[RISK] FolderService ловит saveAndFlush constraint failure и перечитывает в той же @Transactional области; это не доказательство восстановления после DB rollback-only/aborted transaction. Rename/move папки могут получить constraint error при позднем flush за пределами try/catch. Конкурентные folder moves не сериализованы; SQL запрещает только self-cycle. Подробнее DATA-03/DATA-04 в реестре рисков.
