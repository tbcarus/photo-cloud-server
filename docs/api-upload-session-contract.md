# Upload Sessions API — S1

Статус: `SERVER_ONLY`. Android пока использует прежний multipart. Все операции требуют JWT, работают только с сессиями текущего владельца; чужой UUID возвращает 404. Базовый путь: `/api/v1/upload-sessions`.

## Создание

`POST /api/v1/upload-sessions`, JSON:

```json
{
  "clientRequestId": "d0859bf7-1a5e-454f-9397-3d1cf9691340",
  "folderId": 7,
  "originalFilename": "video.mp4",
  "size": 62914560,
  "checksum": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "backupSource": null
}
```

Все поля, кроме `backupSource`, обязательны. `clientRequestId` — UUID клиента; `size` — целые байты, строго больше `storage.max-file-size-bytes` и не больше `upload.max-file-size-bytes`. SHA-256: 64 hex-символа, регистр при сравнении не учитывается, сохраняется нижний. Имя и папка проверяются по существующим правилам File API, в том числе Camera и активного источника резервирования. Shared Read не даёт права загрузки. Папка не выбирается автоматически.

Ответ 200: новая либо существующая сессия. Уникальность — `(userId, clientRequestId)`. Повтор с теми же параметрами возвращает текущую сессию, в том числе терминальную. Другое имя, папка, размер, checksum или backupSource — 409 `REQUEST_MISMATCH`. Повтор не продлевает TTL. После удаления результата по TTL ключ может быть использован заново.

## Состояние и DTO

`GET /api/v1/upload-sessions/{id}` → 200. GET не продлевает TTL, не ждёт получения блока или хеширования и не возвращает служебные пути.

```json
{
  "id": "bc97ddbf-6c20-4961-9b31-e3a8d883720d",
  "clientRequestId": "d0859bf7-1a5e-454f-9397-3d1cf9691340",
  "folderId": 7,
  "originalFilename": "video.mp4",
  "size": 62914560,
  "checksum": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "backupSource": null,
  "confirmedOffset": 8388608,
  "state": "UPLOADING",
  "createdAt": "2026-11-14T06:00:00Z",
  "lastActivityAt": "2026-11-14T06:01:00Z",
  "finishedAt": null,
  "maxChunkSizeBytes": 16777216,
  "result": null,
  "error": null
}
```

Время — UTC `Instant` с микросекундной точностью. `result` после успеха — сохранённый `FileItemDto` из [File API](api-file-contract.md); это квитанция завершения, а не актуальная версия файла после его последующего rename/move/delete. `confirmedOffset` — число подтверждённых байтов, следующий блок начинается здесь.

| Состояние | Значение |
| --- | --- |
| `UPLOADING` | Принимаются последовательные блоки |
| `FINALIZING` | Устойчивая очередь проверки SHA-256 и регистрации |
| `COMPLETED` | Результат и записи Library зафиксированы одной транзакцией |
| `CANCELLED` | Отмена принята; временные байты удаляются с повторами |
| `FAILED` | Терминальная ошибка; нужен новый clientRequestId |
| `EXPIRED` | Незавершённая сессия истекла по отсутствию активности |

У терминальных сессий смещение — историческое; продолжать запись нельзя. Переходов обратно в `UPLOADING` нет.

## Передача блока

`PATCH /api/v1/upload-sessions/{id}`:

```http
Content-Type: application/octet-stream
Upload-Offset: 8388608
Content-Length: 8388608
```

Тело — raw bytes, без multipart и без обязательного checksum блока. `Content-Length` допустимо не передавать (например, HTTP chunked); Server в любом случае считает фактические байты. Блок непустой, не больше `maxChunkSizeBytes` и остатка файла. Android на следующем этапе должен начинать с блоков 8 MiB; сервер принимает и меньшие блоки, включая последний.

Успех: 200 с новым DTO. Получение блока идёт потоково в отдельный временный файл без транзакции БД. Только после полного получения блок добавляется к файлу сборки, вызывается `FileChannel.force(true)`, затем фиксируется offset. Обрыв/неполное тело не подтверждается. Лишний хвост после аварии до фиксации offset отбрасывается перед следующим приёмом или фоновым обслуживанием; недостающие подтверждённые байты переводят сессию в `FAILED / STORAGE_INCONSISTENT`.

Offset должен точно совпадать с подтверждённым. Повтор уже принятого блока → 409 `OFFSET_MISMATCH`, без повторного добавления. После потери ответа или любого неоднозначного отказа клиент делает GET и продолжает от серверного смещения. Два одновременно изменяющих запроса одной сессии не ставятся в очередь: проигравший получает 409 `UPLOAD_BUSY`. Неверный offset и конкуренция не продлевают TTL.

## Завершение и отмена

`POST /api/v1/upload-sessions/{id}/complete`: если файл ещё не полный — 409 `UPLOAD_INCOMPLETE`. Полный файл переводится в `FINALIZING`, ответ 202. Повтор до окончания также возвращает 202; после окончания — 200 с тем же терминальным результатом. Прикладная очередь в PostgreSQL переживает перезапуск, один фоновый исполнитель последовательно вычисляет SHA-256 и регистрирует файлы. Цикл запускается при старте и каждые `upload.maintenance-interval`; вычисление не удерживает HTTP-запрос или транзакцию БД.

Размер и SHA-256 проверяются по фактическому файлу. Несовпадение → `FAILED / CHECKSUM_MISMATCH`, без FileItem/StoredObject. Права на папку и backupSource повторно проверяются под блокировкой дерева непосредственно перед публикацией. Удалённая папка, отключённый источник или конфликт назначения → `FAILED / DESTINATION_UNAVAILABLE`. Транзитные ошибки диска/БД оставляют `FINALIZING` для повторного обслуживания до TTL.

Дедупликация не изменилась: Camera — владелец + папка + checksum; Library — то же имя и checksum в той же папке. Другие имена или папки дают независимые физические объекты. Старые ограничения существующих повреждённых файлов также не изменены: duplicate не выполняет repair отсутствующих байтов.

`DELETE /api/v1/upload-sessions/{id}` → 200 с `CANCELLED` либо прежним терминальным отказом. Повтор безопасен. Для `COMPLETED` → 409 `UPLOAD_COMPLETED`; файл Library никогда не удаляется этим запросом. Во время активного приёма или финализации → 409 `UPLOAD_BUSY`: отмена не принята, её можно повторить после GET. Если отмена зафиксирована первой, финализация не начнётся.

## Ошибки

Обычные ошибки используют существующий `ErrorResponse`. Специфические ошибки протокола: `code=UPLOAD_SESSION_ERROR`, `message` — стабильная причина из таблицы. Асинхронные терминальные ошибки приходят в поле `error` DTO при GET/complete, HTTP 200.

| HTTP | Причины/условия |
| --- | --- |
| 400 | Невалидные JSON, имя, обязательные поля/заголовки, Content-Length: 0, размер для multipart |
| 401 | JWT отсутствует или недействителен |
| 404 | `UPLOAD_SESSION_NOT_FOUND`, чужая/отсутствующая папка |
| 409 | `REQUEST_MISMATCH`, `OFFSET_MISMATCH`, `UPLOAD_BUSY`, `UPLOAD_NOT_WRITABLE`, `UPLOAD_ALREADY_FULL`, `UPLOAD_INCOMPLETE`, `UPLOAD_COMPLETED`, `STORAGE_INCONSISTENT`; действующие конфликты папок |
| 413 | `FILE_TOO_LARGE`: файл, блок или фактически прочитанное тело больше допустимого |
| 415 | PATCH без `application/octet-stream` |
| 429 | `UPLOAD_CAPACITY_EXCEEDED`: исчерпан бюджет незавершённых сессий |
| 503 | `UPLOAD_BUSY`: заняты все приёмники блоков; повторить позже |
| 500 / обрыв соединения | Ошибка I/O/БД, неполная передача или фактически пустое тело без Content-Length; результат уточнить через GET |

## Лимиты, хранение и восстановление

Значения по умолчанию находятся только в `application.yml`:

| Параметр | Значение |
| --- | --- |
| `storage.max-file-size-bytes` | 52428800 (50 MiB), multipart включительно |
| `spring.servlet.multipart.max-file-size` | Ссылка на `storage.max-file-size-bytes`, в байтах |
| `spring.servlet.multipart.max-request-size` | 51 MiB: 50 MiB данных + 1 MiB служебных полей |
| `upload.max-file-size-bytes` | 21474836480 (20 GiB), включительно |
| `upload.max-chunk-size-bytes` | 16777216 (16 MiB), включительно |
| `upload.max-reserved-bytes` | 42949672960 (40 GiB), сумма ожидаемых размеров неочищенных сессий |
| `upload.max-concurrent-chunks` | 4 |
| `upload.inactivity-ttl` | P30D |
| `upload.result-ttl` | P30D |
| `upload.maintenance-interval` | PT10S |

40 GiB позволяют держать два максимальных файла; при исходном пороге 50 MiB это также ограничивает число незавершённых сессий. Четыре приёмника ограничивают одновременно получаемые временные блоки 64 MiB. Если удаление временных блоков не удаётся, они сохраняются до повторной очистки; общий резерв их сессий не освобождается. Бюджет учитывает ожидаемые размеры, а не является квотой всех опубликованных данных Library. Перед приёмом проверяется свободное место для временного блока и добавления к сборке; другие операции/программы всё равно могут исчерпать диск и вызвать I/O-отказ.

Активность — создание, успешно подтверждённый блок, первый complete. GET, повторы complete/create и неуспешные запросы её не продлевают. Неактивная сессия становится `EXPIRED`, временные файлы очищаются. `COMPLETED`, `CANCELLED`, `FAILED`, `EXPIRED` сохраняются 30 суток от `finishedAt`, а при неудачной физической очистке дольше, до её успеха. Завершённые результаты также сохраняют clientRequestId на этот срок.

Служебные данные: `{storage.root}/.upload-sessions/{sessionId}.data` и `.chunk`; клиент пути не задаёт. Они не являются файлами Library и не доступны download/sharing. Одно локальное хранилище, один процесс Server; требуется поддержка hard links на томе storage. Публикация создаёт только новое конечное имя, никогда не заменяет существующее. Исходный файл сборки остаётся до завершения/очистки.

Перед hard link путь публикации фиксируется отдельной короткой транзакцией. Создание FileItem/StoredObject и `COMPLETED/result` — одна транзакция под существующей блокировкой ROOT. Перед следующим изменением дерева восстановление проверяет журнал: для `COMPLETED` сохраняет конечный файл; для незавершённой публикации удаляет конечную ссылку только при `Files.isSameFile` с файлом сборки. Затем журнал очищается отдельной транзакцией, чтобы отказ следующей Library-операции не отменил восстановление. Если восстановление невозможно, изменение дерева отклоняется до успешного повтора. Это не общий журнал rename/move/delete Library.

Гарантии проверены для прерывания процесса; утрата носителя, ручное изменение storage, перенос корня с незавершённым журналом и потеря питания не покрываются обещанием сохранности. Успешный `force(true)` требует корректного выполнения гарантий файловой системой/оборудованием.

## Android-интеграция после S1

Необходимо отдельно реализовать общий выбор multipart/resumable по 50 MiB, блоки 8 MiB, устойчивые clientRequestId/UUID и очередь на Android, GET после неоднозначных отказов, ожидание FINALIZING и отмену с обработкой 409. Более 20 GiB — явный пропуск. Существующие Android-пределы 100 MiB в SAF/Library ещё не изменены: файлы между 50 и 100 MiB сейчас получают серверный 413. Сквозная докачка пока не реализована.
