# S1 — серверная возобновляемая загрузка

Дата: 2026-11-14. Реализован серверный этап; Android не изменён. Git-коммиты не создавались. Рабочий Server 8080, его PostgreSQL и storage не использовались.

## Результат и границы

Добавлен общий протокол для Camera, автоматических источников и ручной Library: создание сессии, состояние, последовательные блоки, асинхронное завершение и отмена. Сессия, подтверждённое смещение и квитанция завершения сохраняются в PostgreSQL, незавершённые байты — в постоянном служебном каталоге storage.

Новые таблица и ограничения создаются Liquibase (`20-upload-sessions.sql`). Переноса старых данных нет. Существующие правила FileItem/StoredObject, владения, имён, физического дерева, Camera/Library-дедупликации и backupSource сохранены. Дата съёмки видео, Android Camera detection, SAF и Library UI не менялись. Ограничения остальных операций Library из Q-03 не устранялись.

API: `POST /api/v1/upload-sessions`, `GET/PATCH/DELETE /api/v1/upload-sessions/{id}`, `POST /api/v1/upload-sessions/{id}/complete`. PATCH использует raw octet-stream и `Upload-Offset`; clientRequestId принят как UUID. Полный контракт, ответы, поля и правила клиентских повторов: [api-upload-session-contract.md](api-upload-session-contract.md).

## Архитектурные решения

| Решение | Предотвращаемая ошибка и причина |
| --- | --- |
| Постоянная сборка + отдельный принимаемый блок | Обрыв тела не загрязняет подтверждённую часть; сетевое чтение не удерживает транзакцию PostgreSQL |
| force(true) сборки перед фиксацией offset | Успешный ответ не опережает запись подтверждённых байтов |
| Отбрасывание неподтверждённого хвоста | Перезапуск между append и COMMIT offset не дублирует блок |
| FAILED при недостатке подтверждённых байтов | Сервер не продолжает с фиктивного прогресса и не публикует неполный файл |
| FINALIZING в БД, один фоновый исполнитель | Хеширование больших файлов не зависит от HTTP timeout; очередь восстанавливается после рестарта и не растёт в памяти |
| Hard link вместо перемещения сборки | После rollback исходные байты остаются; не нужна вторая физическая копия файла до 20 GiB |
| Путь публикации в отдельной короткой транзакции | После прерывания до COMMIT известна возможная конечная ссылка |
| FileItem/StoredObject и COMPLETED/result в одной транзакции | Потеря ответа/повтор complete не создают второй файл |
| Восстановление под существующей блокировкой ROOT | Родительскую папку нельзя переместить вместе с незавершённой публикацией и потерять её путь в журнале |
| isSameFile перед удалением незавершённой ссылки | Занятый чужой файл не удаляется и не присваивается сессии |
| Адресное обнуление publicationPath | Восстановление не перезаписывает одновременно принятую отмену старым снимком сущности |
| Бюджет ожидаемых размеров и ограниченные приёмники | Число незавершённых сессий и временные байты ограничены без произвольных лимитов на каждую папку/источник |

Прежнего `publishSaved` недостаточно для этого протокола: он перемещает temp до COMMIT, а при неизвестном исходе оставляет возможный orphan. Повтор resumable должен сохранить источник и однозначно разрешить публикацию. Повторное использование только имени/checksum не доказывает владение физическим файлом и не защищает от переносов дерева.

Вмешательство в существующий код ограничено отдельным методом регистрации подготовленного resumable-файла в FileItemService и вызовом восстановления из `FolderService.lockUserTree`. Дедупликация, имя, сохранение метаданных и пути используют прежние helpers. Новых зависимостей, распределённых блокировок или общего журнала операций Library нет.

## Состояния и восстановление

`UPLOADING → FINALIZING → COMPLETED`. Терминальные альтернативы: `CANCELLED`, `FAILED`, `EXPIRED`.

- Потерян ответ PATCH: GET показывает зафиксированный offset; повтор старого offset отклоняется 409.
- Обрыв блока: offset прежний; следующий PATCH начинает с него.
- Лишние байты после аварии: сборка обрезается до offset. Недостающие байты: FAILED / STORAGE_INCONSISTENT.
- Прервано хеширование: FINALIZING остаётся, SHA-256 рассчитывается заново.
- Hard link создан, COMMIT не выполнен: собственная конечная ссылка убирается, сохранённая сборка публикуется повторно после проверки.
- COMMIT выполнен, ответ потерян: COMPLETED и квитанция уже в БД; конечный файл сохраняется.
- Отмена принята первой: публикация не выполняется. Активная операция: 409 UPLOAD_BUSY, отмена ещё не принята. COMPLETED: отмена всегда 409 и не удаляет Library.
- Ошибка физической очистки: запись и резерв остаются, следующий проход повторяет удаление. Неопознанные файлы не удаляются.

GET, повтор create/complete и отклонённые запросы не продлевают TTL. Квитанция — исторический FileItemDto: последующий rename/move/delete файла не меняет сохранённый результат.

## YAML и System SPEC

| Параметр | Значение по умолчанию |
| --- | --- |
| Multipart файл | 52428800 байтов, 50 MiB; Spring ссылается на `storage.max-file-size-bytes` |
| Multipart запрос | 51 MiB с накладными расходами |
| Resumable файл | 21474836480 байтов, 20 GiB |
| Блок | 16777216 байтов, 16 MiB |
| Общий резерв неочищенных сессий | 42949672960 байтов, 40 GiB |
| Одновременные приёмники | 4 |
| TTL без активности / результата | P30D / P30D |
| Фоновое обслуживание | PT10S |

40 GiB позволяют два максимальных файла; минимальный размер resumable также ограничивает число незавершённых сессий. Четыре приёмника дают до 64 MiB одновременно принимаемых временных блоков. Ошибки удаления могут оставлять дополнительные временные блоки до повторной очистки; резерв их сессий не освобождается. Это бюджет незавершённых загрузок, а не квота всей Library. Проверка свободного места не резервирует диск от других операций.

Значения заданы в YAML, новый UploadProperties выполняет только привязку/валидацию. Дублировавшийся Java-default multipart-лимита удалён.

System SPEC: обновлены модель, backup, Library, recovery и индекс сценариев. Добавлены BACKUP-RESUMABLE, FILES-RESUMABLE, SYSTEM-UPLOAD-RECOVERY со статусом IMPLEMENTED и доступностью SERVER_ONLY. Старые клиентские ограничения 100 MiB сохранены как описание существующего Android и явно отделены от нового серверного multipart-предела 50 MiB.

## Ограничения и Android-интеграция

- Требуются один процесс Server, локальный том с hard links и неизменный storage root на время незавершённых публикаций. Проверено на текущей Windows-машине; переносимость и поведение сетевых ФС не заявлены.
- Журнал публикации/восстановления кратковременно использует дополнительное соединение БД через REQUIRES_NEW; нагрузка при исчерпании пула не измерялась. Инфраструктурные отказы повторяются, состояние не объявляется завершённым до COMMIT.
- Потеря питания/носителя, ручное изменение storage и восстановление данных из несогласованных резервных копий не проверялись. При утрате источника незавершённой публикации возможна необходимость ручного восстановления: Server не удаляет неопознанные байты.
- Не выполнялся прогон реального файла 20 GiB и нагрузочное измерение времени хеширования. Лимит проверен без такого файла, потоковая передача и восстановление — на небольших файлах.
- Дедупликация не исправляет прежнюю запись Library с потерянными байтами; общий Q-03 остаётся отложенным.
- Android ещё должен получить централизованный порог 50 MiB, блоки 8 MiB, устойчивые clientRequestId/UUID/очередь, GET после неоднозначных ошибок, ожидание FINALIZING и обработку отмены. Более 20 GiB — явный пропуск. До этого файлы 50–100 MiB старого SAF/Library-клиента получают серверный 413.

Принципиальных неразрешённых архитектурных развилок S1 не осталось. Клиентский этап и продуктовые правила его UI этим изменением не реализованы.
